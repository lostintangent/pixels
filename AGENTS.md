# Pixels engineering decisions

- Source of truth: the shared Pixels spec in the Toy Box channel. Keep features public through their `index.ts` and framework-free `core/` modules.
- Bun remains the package manager, test runner, and perf runner. Vite+ runs dev and build (`vp dev`, `vp build`) under Bun, and owns Oxlint and Oxfmt (`vp check`). A bounded Bun-native spike proved StyleX and Astryx CSS compile and live StyleX CSS reloads when the generated file enters Bun's asset graph. TanStack Router then crashed in Bun's HMR module loader on an import cycle: `Cannot read properties of null (reading 'replaceRouteChunk')`. This is [Bun issue #40378](https://github.com/oven-sh/bun/issues/40378). The required router cannot run in Bun's dev server until that is fixed. Revisit Bun-native bundling when bun#40378 closes and a browser smoke test passes with the then-current TanStack Router.
- The Vite+ StyleX plugin handles production CSS extraction. In development the HTML plugin loads `/virtual:stylex.css` and `virtual:stylex:runtime` so style edits update live.
- Our StyleX classes use the `p` prefix (`classNamePrefix` in `src/shared/build/stylexOptions.ts`, which the build and the guard share). Astryx ships StyleX output precompiled with the default `x`, and atomic class names hash only the property and value, so 174 of our classes had the same names as Astryx's. Ours sit in later `priority` layers, so each base declaration overrode the states Astryx attaches to the same class. Before the change, keyboard focus and hover on menu and submenu items showed no background. Focusing the picker's "Close popover" kept it invisible. The phone width slider had no focus ring. Segmented controls lost their hover fill, the selected item kept the `--shadow-low` that the neutral theme's `astryx-theme` layer sets to `none` (our `priority4` copy of `x1i5ehqx` outranked it), and under forced colors the selected item was white on white. With the prefix, Lead's `collide2.py` finds 0 lost states instead of 171 on the production CSS. A before and after capture of every Astryx surface at desktop 2× and phone 3×, light and dark, changed only those states. Everything else was identical, or differed only by edge-shadow speckle that also appears between two runs of the same build. Reduced-motion durations and disabled cursors measured the same on every surface we render. `src/shared/build/astryxClasses.test.ts` compiles every app source through the same Vite StyleX plugin and options and fails on any class that also appears in the CSS `src/app/global.css` imports. With `PIXELS_STYLEX_PREFIX=x` it reports the 174 collisions.
- Pixels requires Bun 1.4.3-canary.1 (4b02e1031) or newer. Stable Bun 1.4.2 (744846f84) miscompiles the end-of-input check in StyleX 0.19.1's bundled CSS tokenizer (`void 0 === source.codePointAt(cursor)` returns false at the real end of input once the JIT warms up). The dev server then answers 500 with "Invalid media query syntax" for files transformed later, which were the lazy dialogs and color picker. A one-line patch to `cursor >= source.length` worked around it until 2026-10-01. That day the canary passed all 200 varied transforms in `src/shared/build/stylex.test.ts` and a forced cold dev-server load of New, Resize, Export, and the color picker, and production output was byte-identical with and without the patch, so the patch was dropped. The test stays as the tripwire: under 1.4.2 it fails at fixture 20 with a message to run `bun upgrade --canary`. Its 200 sources vary so an identical-source cache cannot hide the bug. If a later Bun regresses, restore the patch through `patchedDependencies` rather than pinning an older Bun.
- The dev and preview servers listen on every interface and accept `*.ts.net` hosts (`server` in `vite.config.ts`), so devices on the tailnet can open them. Plain HTTP is not a secure context, so browser code must not depend on secure-only APIs such as `crypto.randomUUID`. Use `createDocumentId` from files. Export feature-detects the share sheet and downloads instead.
- Performance budgets are p95 gates on deterministic fixtures. Report the machine, command, and actual measurements before changing any budget. Never widen a budget just to pass a run.
- Fit uses the largest whole-number zoom at or above 1×, bounded by 128×. Below 1× it keeps the largest whole percentage that fits, at least 1/32, because zoom-out is area-filtered rather than nearest-neighbor. This makes a 16×16 phone canvas 22× and a 32×32 canvas 11×, with exact square pixels, and a 1990 px Retina screenshot 54% on desktop and 17% on phone instead of 50% and 12.5%. An island within 12 px of the centered fit blocks it. The fallback shrinks around the same center to the largest such zoom that keeps 12 px clear of every island, and moves beside the island, with the same gap, only when that would be smaller. Zoom buttons and wheel steps move to the next ladder value above or below an off-ladder fit. The viewport carries an exact fitted label until a finished zoom clears it. A pinch that began at a fit carries that fit while it moves, and the label snaps to the same candidates as the settle (ladder, floor, and that fit), so it always names where the gesture will rest and chrome still updates only when that destination changes. An untouched fit refits when the viewport or measured islands change; manual pan or zoom preserves the artist's view. An external Fit cancels a pending pinch settle so it cannot later snap the fitted view onto the ladder.
- The canvas can't get lost. Zoom-out stops at the smaller of 1× and the island-aware Cmd+0 fit, so a 32×32 sprite stops at 1× and the 1738 × 1032 P3 screenshot at 63% on desktop and 20% on phone. On each axis the document keeps overlapping the fit frame by a quarter of the frame, or entirely when it's smaller. The math lives in `canvas/core/bounds.ts` and stays out of the renderer. The editor session supplies the limits, cached on frame size, layout, islands, and document size. Buttons, keys, wheel steps, and wheel pan stop hard at a limit, and a stopped wheel writes nothing, so momentum can't jitter. Space-drag, middle-drag, and two-finger touch stretch past a limit with a 0.55 rubber band against the frame size, and a pinch below the floor gives at most a factor of 2 in log space. On release a pan eases back in 200 ms and a pinch settle snaps to the ladder, the floor, or the zoom the pinch started from, inside the bounds. That start candidate keeps an off-ladder fit, such as a 32×32 sprite's 11× on phone, through a two-finger pan or a pinch of a few percent, along with its fitted label, instantly under reduced motion. A view already inside returns the same object, so in-bounds moves allocate nothing. A manual view keeps its zoom on resize and only its pan re-clamps, unless the window grows enough to raise the floor past it. Island changes don't re-clamp on their own. In headed Chromium on the M1 Max, `bun run perf:app` kept the same eligible frames (desktop pan 277/277, phone pan 276/276) with main p95 0.492 and 0.450 ms, and `perf:browser --fixture-only` passed all 9 scenarios.

- Feature-boundary and framework-free core imports are enforced by `lint/feature-boundaries.js` through `lint.jsPlugins`. A deliberate private cross-feature import produced `error boundaries(public-feature-imports)` in `vp lint`; the import was then removed.
- Full-canvas history swaps the document's pixel buffer. Consumers read `pixels` and `rgbaBytes` again after undo/redo; the renderer rebinds `ImageData` when the buffer changes. Line previews use a compact workspace that the editor can reuse across gestures. Overlay-only changes bypass document upload and viewport compositing, and only the marquee has an animation timer.
- Paste and Duplicate start a floating selection without changing document pixels. Moving it only changes overlay bounds; commit captures the destination and makes one undo step, while Cancel or Clear discards the paste without a history entry. Lifted moves also leave the committed document untouched until commit, so autosave and reload keep the source art. Leaving for another document (New, Open, Open recent, Back) commits the float first, like a tool change, so the move the artist saw is what gets saved. The overlay covers that source with a checker and draws the floating pixels at their target. Commit captures and clears the source, then pastes the target in one history step; Cancel leaves the bytes identical. Opening Export commits the float before the dialog preview snapshots pixels, and the PNG action calls `commitFloatingSelection()` again as a guard. The in-app clipboard outlives editor sessions, so each session seeds `hasClipboardPixels` from it; Duplicate never writes to it. A paste keeps its saved origin only when fully inside both document and viewport, then otherwise centers in the visible document area.
- Flood fill compares through a signed `Int32Array` view of the same buffer. Opaque ABGR values otherwise take JSC's double-number path. On the 1024² winding maze this changed p95 from 23.5 ms to 3.1 ms. The neighbor scan remains bounded to the current span; a global `indexOf` was faster on the maze but could scan unrelated rows. A source color occupying at least 75% of the canvas takes one full history snapshot; smaller populations keep tile snapshots.
- Core perf uses warmed p95 samples in three blocks with GC before each block. The gate uses the median block p95 and prints all three plus the machine load average, so a single system burst is visible without deciding the result. Undo/redo cases exercise tile snapshots from a 16 px stroke and a 2048² fill, with fixture assertions that reject accidental full-buffer history. Selection measures the full lift, move, and drop gesture. Existing budgets in `core-cases.ts` remain no looser than the spec targets. New end-to-end cases have targets at most 1.5× the observed loaded-machine p95 and need corresponding spec rows. `bun run perf --repeat 5` is the repeatability gate on the reference machine.
- Browser perf builds the real engine fixture separately into `dist-perf` and traces production Chromium with Playwright CDP at 1440×900 @ 2× desktop and 390×844 @ 3× phone. The default is headed Chrome because it follows the hardware-composited user path; the runner logs the WebGL renderer, Chrome version, mode, load average, and measured refresh rate. Headless with Metal flags still showed higher canvas pipeline work in the measured session, so it remains a diagnostic (`--headless-gpu`). Frame windows come from Chrome's main-frame trace events. The p95 gate uses renderer-main `RunTask` time because the spec targets main-thread work, while the printed aggregate pipeline CPU includes compositor, raster-worker, and GPU-process tasks as a diagnostic. The 50 ms renderer-main long-task gate is strict in every block. For draw and pan, Chrome's `PipelineReporter` states gate at least 99% presented frames without high latency, with no consecutive drops; `STATE_NO_UPDATE_DESIRED` does not count as an eligible frame. All scenarios warm their canvas/GPU resources before tracing.
- `bun test` walks a `Bun.build` metafile for every feature `core/` module and rejects transitive imports of React, StyleX, Astryx, or another feature's UI. This caught the palette-index leak that a direct-import lint rule missed.

- Files feature (`src/features/files`): PNG is decoded/encoded as raw RGBA bytes with zero repacking, because `BitmapDocument.rgbaBytes` is a `Uint8ClampedArray` view over the same buffer as `pixels` and reads as literal R,G,B,A on little-endian, matching PNG's byte order exactly. `CompressionStream`/`DecompressionStream('deflate')` produce real zlib streams, so IDAT needs no hand-rolled DEFLATE. Autosave snapshots the live document synchronously (`snapshotDocument`), before any `await`, because strokes and undo can swap the document's buffer between microtasks. A document store `save()` only deletes a document's existing tiles when the snapshot is a full resave, so an incremental save never touches tiles outside its own dirty set, and a resize/shrink can't leave stale pixels at the old bounds. Multi-tab editing of the same document is a deliberate exclusion: the last tab to autosave wins, with no cross-tab lock or merge. `bun test` runs the real IndexedDB adapter directly against `fake-indexeddb` (no separate fake/port), since Bun has no native `indexedDB` global.
- The exact PNG decoder uses slicing-by-8 CRC32, preserving per-chunk corruption checks, and decodes non-interlaced RGBA8 rows directly into the final pixel buffer. Filter-0 rows use a typed-array copy. Non-interlaced RGB8 rows reuse two scratch buffers and expand through packed 32-bit writes, preserving tRNS color keys. Other bit depths, color types, and Adam7 keep the general decoder. On the M1 Max with headed Chrome 153, three production runs per size cut file-event-to-first-draw median from 562 to 351 ms at 3456 x 2234 and 1167 to 714 ms at 4096². Worker parse/CRC fell from 67/146 to 45/99 ms, and unfilter plus RGBA expansion from 188/409 to 4/8 ms on those filter-0 photo fixtures. A 312-case corpus exercises every PNG filter across widths, heights, partial alpha, and hidden RGB; an RGB8 test covers all filters and tRNS. The real P3 screenshot and photo output hashes stayed byte-identical. `bun test` passed 368/368, `golden:export` passed sRGB/P3, and `perf:import` passed all 26 runs with no main-thread task over 50 ms at load average up to 32.86. Streaming unfilter was left out because this simpler path passed the requested target without changing inflate behavior or error handling.
- PNG color chunk precedence is `cICP` > `iCCP` > `sRGB` > default sRGB, and whichever chunk is present wins outright even when unrecognized: an unrecognized `cICP` or `iCCP` classifies as `unknown-icc`, never falling through to a weaker chunk or guessing sRGB, since the file is handing us real color information a silent sRGB default would misrepresent. `cICP` `[12,13,0,1]` (Display P3) and the plain `sRGB` chunk were verified against real macOS `sips -m`-tagged PNGs; `cICP` `[1,13,0,1]` for sRGB is the documented H.273 convention only, since real sRGB exports from that tool skip `cICP` entirely. `iCCP` decompresses the embedded ICC profile and reads its `desc` tag (both legacy ASCII and ICC v4 `mluc`), matching `"p3"`/`"srgb"` substrings; any parse failure also yields `unknown-icc`, never a throw. `colorTag.ts` keeps its own private `inflateZlib` rather than importing `png.ts`'s, to avoid a circular import. An `unknown-icc` profile converts to Display P3 (not sRGB) via `createImageBitmap` onto a `display-p3`-tagged canvas, since the wider space minimizes clipping for an unrecognized profile's own gamut; this returns `null` (never throws) when DOM APIs are unavailable, e.g. under `bun test`, and import falls back to sRGB with the already-decoded pixels. Export writes `cICP` for `display-p3` documents and plain `sRGB` for `srgb`, never both and never an embedded `iCCP` blob, to avoid bundling a binary profile.

- First-load JS: rare surfaces (New, Resize, Export dialogs and the full color picker) load through `shared/react/deferred`, mount on first open, and stay mounted so exit motion plays. Each feature has one lazy module (`editor/ui/dialogs/all.ts`, `palette/ui/picker.ts`) because Rolldown hoists code shared by two lazy chunks into a chunk the entry loads, which put `ColorPicker` back on the first load. Astryx statically imports its full English catalog (1,110 messages) and `intl-messageformat`, about 30 KiB gzip. `shared/build/astryxMessages` keeps only the messages bundled Astryx modules reference (19 at the time) and swaps in a `{name}` / `{name, number}` formatter. The build fails if a reachable message needs plural, select, or other ICU syntax. Together these moved initial JS from 247.4 to 207.6 KiB gzip. Source-map attribution showed 62 KiB react-dom, 26 KiB TanStack Router/history/store, and about 29 KiB Astryx theme runtime/hooks in that initial JS. The lead set the ratchet at 170 KiB for entry and static imports, and 40 KiB for initial CSS, after reviewing that floor against the user's chosen stack.
- The neutral theme registers 28 Lucide icons, and Astryx core bundles a fallback SVG for each, all on the first load. `shared/build/astryxIcons` keeps only the theme icons listed in `THEME_ICON_NAMES` and empties the fallback set, since the theme supplies every icon the app asks for. The guard over-approximates: any quoted word in a bundled Astryx module's code (whole-line comments skipped) that names a registered theme icon counts as asked, and the build fails if the list would prune it. A narrower `icon:`/`useIcon` match at `4163927` missed field statuses, which map `error`, `warning`, and `success` through lookup tables, and blanked those icons. `menu` and `search` are kept only because ARIA roles and input types quote them; a false positive costs bytes, a miss ships a blank state. The scan runs in `transform` on code already in memory. With nine icons kept, initial JS is 165,742 gzip bytes, 345 more than the six-icon cut. Every SVG in the editor, menus, dialogs, popovers, field statuses, and toasts on desktop and phone serializes identically to the unpruned build.
- Vite's automatic module preload maps included repeated paths to JS already in the entry's static graph. `shared/build/modulePreload` walks that graph at build time and filters only those paths from the dynamic preload lists, preserving lazy JS and CSS parallel fetches. If the graph is unavailable, it retains Vite's full list so the size gate catches a regression. The modulepreload polyfill is disabled because browsers supported by Pixels already need native `light-dark()`. The combined shape-persistence build measured 169.838 KiB initial JS, under the unchanged 170 KiB gate. In headed Chrome, five cold opens per case measured median full-preload → filtered times of Fill 277→271 ms, Shapes 144→142 ms, Export 393→405 ms on a local network; at 100 ms simulated RTT they were 273→280, 242→249, and 495→499 ms. First-open Shapes, Export, and color picker were styled when they appeared. The generated preload maps retained lazy chunks and CSS while excluding entry-graph JS.
- Rolldown's `$initial` code-splitting group folds the modules the entry always loads into one JS file. At `943476e`, this reduced gzip-level-9 initial JS from 174,076 bytes across ten files to 168,608 bytes in one, with the same lazy surfaces and separate PNG and preview workers. An isolated headed `bun run perf:app` passed cold first stroke p95 263.9 ms, all four input gates, and 1,158/1,158 presented input frames; `bun test` passed 375/375 and `bun run check` was clean. A production-browser smoke opened Shapes, New, Export with preview, and the color picker without page or request errors. Combined with the later icon and opening-state work, a production build measured 165,397 bytes of initial JS and 38,104 bytes of CSS. Keep the 170 KiB JS and 40 KiB CSS limits unchanged; lazy surfaces and workers must remain separate when changing this group.
- `perf:app` builds the production app with a Vite manifest, serves it through `vp preview`, and uses headed Chromium. Load time begins at navigation and stops at the first real pointer stroke changing a viewport pixel. Three cold/warm cache pairs per block, three blocks per run, report the median of block p95 values. Initial JS and CSS count gzip level 9 bytes from the manifest entry and its recursive static imports; dynamic imports and idle prefetch stay outside the size gate, while transfer through first stroke remains visible as a diagnostic. The 500 ms load and initial size budgets are independent gates; a failure stays red. Real editor input creates a 1024² document through the UI, zooms to 8×, selects a 16 px brush, then traces actual pointer strokes and pan gestures at desktop 2× and phone 3×. Each scenario uses three trace blocks with app-specific Chrome main-thread limits and the same frame-presentation and long-task gates as the renderer fixture. The phone pinch moves one finger against a stationary finger, which still exercises simultaneous pan and zoom with a realistic touch event rate. Calibration prints failed gates without changing their limits.
- `perf:app` runs one background `yes` worker during the real-editor input scenarios, starting after the load and size gates, to condition macOS CPU scheduling without stealing user focus. It prints the worker PID and stops it in `finally` and on process exit; `--unconditioned` is diagnostic. On this M1 Max, one worker changed desktop stroke main p95 from 4.083 ms on an idle headed Chromium in the background to 1.143 ms, while all 363/363 input frames presented. A CPU-load BUSY verdict was removed: 18 and 30 workers pegged external CPU near 98% yet all frame scenarios passed, whereas quiet failures had no contention signature. A retained trace found that each apparent partial frame was a forked `PipelineReporter` duplicating a complete primary reporter; the parser now prefers the primary in either event order. `--inject-stroke-ms N` adds synthetic desktop pointer-move work only inside trace blocks to verify that a real regression still fails. `PIXELS_PERF_TRACE_DIR` optionally saves a failing Chrome trace. No frame budget was widened.
- The user accepted calibrated app main-thread limits on 2026-09-30: desktop stroke < 1.95 ms, desktop pan < 0.8 ms, phone stroke < 0.9 ms, and phone pan < 0.75 ms, tightened from the original 4/3 ms app targets. Engine's two six-repeat conditioned runs observed maxima 1.320, 0.544, 0.645, and 0.528 ms, and the lead's independent six repeats (one at load average 31) observed 1.248, 0.498, 0.631, and 0.551 ms. Every limit is at most 1.5× its observed maximum. Phone pan has the least headroom (1.36×). All 72 frame scenarios passed with 100% fully presented eligible frames. A synthetic 1 ms per-move desktop stroke fails (p95 2.111 and 2.226 ms), and 2 ms fails at 3.106 ms. The renderer fixture now conditions its traced input too, with stricter limits documented below.
- `perf:browser` now runs one `yes` worker during the renderer fixture, stops it before `perf:app` starts its own input worker, and keeps `--unconditioned` for diagnosis. On the M1 Max in headed Chromium 153, five conditioned repeats at desktop 2× and phone 3× measured median-block main p95 maxima of desktop 0.397/0.296/0.307/0.302 ms and phone 0.344/0.295/0.308/0.278 ms for stroke, pan, 4096² fit-pan, and shape-handle drag. New respective limits are 0.59/0.44/0.46/0.45 ms desktop and 0.51/0.44/0.46/0.41 ms phone, each strictly below 1.5× its observed maximum. All 9,842 eligible frames across those calibration runs were fully presented. A second strict `bun run perf:browser --fixture-only --repeat 5` passed all 45 measured scenarios and all eligible frames. `--inject-large-pan-ms 1` failed the 0.46 ms gate on both profiles at 1.294 and 1.285 ms (exit 1). The existing 50 ms task and ≥99% frame gates remain. The old 4/3 ms renderer targets and older unconditioned fit-pan and handle-drag numbers in this file are historical.
- The app perf build uses a private temporary output directory so other builds cannot replace its files during a run. One discarded navigation warms the preview server before cold-cache blocks. Pixel correctness uses a clipped compositor screenshot after the measured stroke blocks, and the load gate uses compositor screenshots to verify its first stroke. Reading the app canvas with `getImageData` inside a trace caused a 43 ms GPU readback task and false frame drops; repeated reads can also move a canvas into software mode. Desktop pointer moves cache the host's screen origin for the gesture, refreshing it on resize, scroll, and visual viewport changes. A CPU profile found `getBoundingClientRect` on every move after the position pill wrote text, forcing layout; caching avoids those repeated reads while keeping coordinates current.
- `perf:import` uses the production app and headed Chrome to open 2400 x 1600, 3456 x 2234, and 4096 x 4096 photo PNGs plus a real Display P3 Mac screenshot at desktop 2× and phone 3×. A 3456 x 2234 case draws a rectangle and arrow and verifies both visible after cold reload. Each run observes Chrome main-thread long tasks from the open gesture through first render and a confirmed IndexedDB autosave, then from cold navigation through the restored first paint. No task over 50 ms is allowed in any run, including under load. The runner reports load average and, on failure, the worst task with Long Animation Frame attribution when Chrome provides it. The annotation readback happens after the observed interval to avoid a false GPU readback task. The first full 26-run headed matrix on the M1 Max passed with no long task at load average up to 64.47; first-render times ranged 198–1288 ms and cold reload 114–246 ms. `--inject-open-ms 60` must fail this gate. The real screenshot is kept as a small checked-in fixture, while large photo fixtures are generated into a temporary directory.
- The lead accepted `perf:import` first-render limits of <500 ms at 3456 x 2234, <1000 ms at 4096², and <250 ms for the real P3 screenshot on 2026-10-01. Gate the median of the default three runs per scenario, with every run printed. The lead independently observed individual loaded-machine outliers of 689/905/248 ms at load average 32 to 83 even as all 26 runs passed, so a maximum-of-three time gate would confuse scheduling noise with a decoder regression. Fewer than three completed runs print a diagnostic time only. The per-run 50 ms main-thread long-task gate remains strict.
- Adopt a PNG Worker's transferred RGBA buffer directly as the document's pixel storage. Before this change, `importPng` allocated and copied another 64 MiB on the main thread for 4096². In a diagnostic Chrome phone run, document creation took 0.4 ms, that copy 5.6 ms, the first full snapshot's thumbnail 1.4 ms and its required safety copy 5.4 ms, and the first paced 512-tile IndexedDB batch 13.8 ms. These occur in the same Worker-response task before the first IndexedDB yield. One of 26 integrated import runs crossed the strict 50 ms task gate at 50.0 ms there; five immediate old-code repeats passed, so do not claim the one-off was fixed solely by the copy removal. Five adopted-buffer phone 4096² runs passed under load average 77–86 with first-render median 582 ms. The document factory accepts initial pixels only when the view starts at byte offset zero and its element and backing-buffer sizes exactly match the dimensions; its `rgbaBytes` view aliases those bytes.
- Open, paste-as-new, and New store the document before navigating to it. A lead experiment at 186a887 started the save, navigated, then awaited the save. In headed `perf:import` at load average 8–12, 4096² first-render medians fell from 580/584 to 487/486 ms (desktop/phone), while 3456 x 2234 moved only from 310/311 to 299/289 ms because the IndexedDB batches then compete with first render. It was not adopted. A failed save, such as a quota error on a 64 MiB image, would leave the artist editing a document that was never stored, and a reload during that window would lose a pasted image that has no source file. Revisit only with a durable first-save error path in the editor and a measurable win at common screenshot sizes.
- Production preview harnesses share `withProductionPreview` in `src/shared/preview.ts`. Vite+ forks the actual preview listener, so killing only the `bunx` wrapper leaves an orphan that holds inherited pipes open and makes piped test commands hang. The helper builds into a private temporary directory, starts preview in its own process group, and stops the entire group with TERM then KILL if needed. SIGINT and SIGTERM handlers stop that group and remove the build directory before exiting 130 or 143. Callers must keep their browser work inside the helper callback, including failure paths.
- Chrome reports `STATE_PRESENTED_PARTIAL` when a frame is shown without all main-thread content. The browser gate counts it as a missed ink frame, alongside drops and high-latency presentations, and prints the state histogram plus per-stage p95 so a red run can be diagnosed. The renderer's dirty-rect viewport redraw was pixel-identical to a full redraw in Chromium but cost more pipeline time (9.16 vs 7.78 ms block-median p95 in a four-way interleaved trace). Cursor-only overlay clearing was a tie after a combined-clip optimization (2.85 vs 2.93 ms across eight interleaved blocks). Both experiments were reverted in favor of the simpler full redraw. The idle full-window drop-overlay backdrop filter was removed separately; real-editor steady pipeline p95 then measured near 3 ms. Keep the first traced 120-point stroke in the gate: partial-presentation bursts have appeared there intermittently, and that cold stroke is a user-visible operation. No warmup stroke or budget exception was added. A clock-sync marker immediately before the first dispatched input defines frame eligibility: a `PipelineReporter` whose frame began at or before the marker cannot reflect that gesture and is excluded. The report remains printed as a pre-input diagnostic. In a twelve-run interleaved phone experiment, full-overlay paint/clear prewarm did not change the frame-1 drop: all six prewarmed and all six controls had it. No prewarm was added to the app.

- Editable annotations live in `annotations/model.ts` as a framework-free feature entry. The browser painter loads only when shapes appear. Each `BitmapDocument` owns one annotation set through a WeakMap, and its committed shapes share the pixel history stack through the history feature's opaque external-state adapter. A resize replaces the bitmap and shifts shape coordinates by the same anchor offset in one undo entry. Shape previews are transient. Flattening renders onto an isolated layer and composites into a copy, preserving every untouched RGBA byte. The selection halo is clipped to the image while handles can extend beyond it. On the M1 Max, `bun run perf:browser --fixture-only --repeat 5` measured 4096² handle-drag main p95 maxima of 0.858 ms desktop and 0.807 ms phone, with all 2,700 eligible frames on time across those shape scenarios. Those were the unconditioned historical gates; the conditioned calibration below tightens them to 0.45 and 0.41 ms. Five isolated Bun core measurements of the oldest-of-200-shapes hit test peaked at 0.001125 ms, so its gate is 0.0016 ms. Existing perf gates remain unchanged.
- A shape stays reachable when at least 8 screen px of its stroke centerline, or its whole centerline if shorter, lies within the closed image box. Strokes centered on the boundary count, because half their width still draws inside. A draw that ends with too little centerline on the image is discarded. A move, handle drag, or nudge stops at the last position that keeps the smaller of 8 screen px and the run the shape already has, so a shape held at a high zoom still holds after zooming out. Only a shape none of whose centerline touches the image moves freely, so it can be brought back. A handle drag keeps the press's offset from the handle's drawn center, so the handle doesn't jump to the pointer. A restyle records its final color in Recent when the 700 ms amend flushes, so a picker drag adds only one entry.
- A mouse press on palette swatches and tool rail buttons doesn't take focus, and a width slider press hands focus back when it ends, as native macOS controls do. Arrow keys then keep nudging the selected shape or selection instead of roving the control that was clicked. Tab still reaches each control with its roving arrow keys.
- Tab toggles chrome only when the canvas (`role="application"`) has focus, or when chrome is already hidden, so Tab from anywhere brings it back. Hidden islands are `inert`, so nothing invisible is reachable. Every New, Resize, and Export surface returns focus to its opener when it closes, by Escape, Cancel, or its action. A menu item closes with its menu, so the opener resolves to the trigger that names the menu in `aria-controls`, or to the `aria-haspopup` trigger beside a phone's sheet menu. When the opener is gone or inert, focus lands on the canvas, and New, Open, and Back hand focus to the next editor's canvas. React StrictMode replays the capture effect after the header has focused its title, so the first capture stands. A native modal `<dialog>` lets the last Tab reach the browser chrome, which reads as focus escaping to the page in every dialog, so surfaces wrap Tab and Shift+Tab themselves. New canvas presets are one roving Tab stop: Left and Right wrap, Up and Down move a row, Home and End jump to the ends. A keyboard walk passed 50/50 checks on desktop in light and dark, and phone sheets returned focus to the document button with Tab kept inside.
- New and Resize share `useSizeFields` from `dialogs/Surface.tsx`. Each edit applies that stored ratio, never the other field, so repeated edits don't drift. An unusable side leaves the other alone. Return in either size field presses Create or Resize with the pair it just committed, read from a ref the setters update synchronously, so it never sees a stale size. It does nothing while either side is unusable, when Resize hasn't changed the size, or when the field still shows a draft it rejected, such as "abc". - Full-fidelity color: `BitmapDocument.colorSpace` tags raw RGBA as `srgb` or `display-p3`. The document, viewport, overlay, preview, and mipmap canvases use that color space, as does `ImageData`.
